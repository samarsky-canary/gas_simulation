# RandomForest RUL: что подается на вход и чему учится модель

Документ описывает ML-слой на высоком уровне: какие данные получает `RandomForestRegressor`, что является целевой переменной и почему мы считаем, что модель обучается именно прогнозу остаточного ресурса фильтра.

## 1. Задача модели

ML-модель решает задачу регрессии:

```text
наблюдаемая телеметрия + расчетные признаки + паспортные параметры -> RUL_oracle_h
```

Выход модели:

```text
RUL_pred_h
```

В гибридном слое это значение используется как:

```text
RUL_ml_h
```

Модель не назначает обслуживание напрямую. Она только оценивает остаточный ресурс в часах. Решение о плановом/срочном обслуживании строится отдельно в UI и гибридной логике.

## 2. Что подается на вход RandomForest

Входы зафиксированы в `src/ml/baseline.py` в списке `ML_INPUT_COLUMNS`.

### Наблюдаемая телеметрия

Это данные, которые в реальной системе могли бы прийти с датчиков:

```text
P_in_MPa
P_out_MPa
deltaP_kPa
Q_m3h
T_C
```

### Паспортные и конфигурационные параметры объекта

Это известные параметры текущего фильтра и сценария:

```text
q_nominal_m3h
p_in_nominal_mpa
dp0_kpa
k_s_per_hour
k_c
beta
gamma_load
```

Они нужны, потому что одинаковая начальная телеметрия может означать разный RUL для разных фильтров и разных скоростей деградации. Например, нормальный режим с малым `k_s_per_hour` должен иметь гораздо больший ресурс, чем быстрый сценарий при похожем начальном `deltaP`.

Это не утечка целевой переменной: эти параметры известны до прогноза и задают физику объекта.

### Инженерные признаки

Это производные признаки из наблюдаемой телеметрии:

```text
deltaP_norm_kPa
deltaP_roll_mean_1h
deltaP_roll_std_1h
deltaP_slope_6h
deltaP_roll_mean_24h
deltaP_slope_24h
deltaP_slope_72h
Q_roll_mean_1h
missing_rate_1h
time_above_warn
elapsed_hours
cumulative_load_h
```

Ключевой признак:

```text
deltaP_norm_kPa = deltaP_kPa / max((Q_m3h / q_nominal_m3h) ** alpha_flow, eps)
```

Он убирает основное влияние расхода на перепад давления, чтобы модель видела рост сопротивления фильтра, а не только изменение режима потока.

## 3. Что не подается на вход

На вход ML намеренно не подаются скрытые и целевые поля:

```text
clog_level
RUL_oracle_h
state
```

Почему:

- `clog_level` - скрытый уровень засорения симулятора, в реальной системе он напрямую неизвестен;
- `RUL_oracle_h` - целевая переменная, которую модель должна предсказать;
- `state` - диагностическое состояние, производная метка.

Если подать эти поля на вход, модель получила бы прямую или косвенную подсказку target. Это была бы утечка данных.

## 4. Целевая переменная

Цель обучения:

```text
RUL_oracle_h
```

Это синтетическая “истина” симулятора: сколько часов осталось до первого будущего достижения критического порога засорения/перепада.

В коде oracle RUL считается назад по временному ряду:

```text
если в будущем фильтр достигает critical:
    RUL_oracle_h = время до ближайшего будущего critical
иначе:
    RUL_oracle_h = NaN
```

В обучение попадают только строки, где `RUL_oracle_h` известен. Поэтому для train-корпуса важно генерировать такие прогоны, которые в пределах горизонта доходят до critical. Иначе у модели не будет target для здоровых длинных участков.

## 5. Как формируется обучающий корпус

Обучение не идет по одному текущему UI-прогону. Генерируется корпус из независимых синтетических прогонов.

В корпус входят сценарии:

```text
normal
slow_clogging
rapid_clogging
flow_spikes
sensor_bias
sensor_stuck
missing_data
```

Для каждого прогона варьируются:

- скорость деградации;
- длительность;
- номинальный расход;
- номинальное давление;
- базовый перепад чистого фильтра;
- параметры сопротивления;
- начальное засорение;
- шумы и дефекты датчиков.

Для `normal` специально генерируются длинные прогоны с малой, но достижимой деградацией. Это нужно, чтобы модель видела большие RUL в здоровом режиме и не сжимала прогноз к типичным значениям деградирующих сценариев.

## 6. Train/test split

Split выполняется по целым `run_id`, а не по случайным строкам.

Правильно:

```text
train = одни независимые прогоны
test = другие независимые прогоны
```

Неправильно:

```text
случайно перемешать строки одного и того же временного ряда
```

Почему: соседние точки одного прогона очень похожи. Если часть одного и того же ряда попадет в train, а часть в test, качество будет завышено. Split по `run_id` проверяет, может ли модель обобщаться на новые траектории.

## 7. Как RandomForest обучается

Используется:

```
RandomForestRegressor (
    n_estimators=120,
    max_depth=14,
    min_samples_leaf=5,
    random_state=42,
    n_jobs=-1,
)
```

Модель строит ансамбль деревьев решений. Каждое дерево учится разбивать пространство признаков так, чтобы уменьшить ошибку прогноза `RUL_oracle_h`.

Оптимизируемая задача регрессии по смыслу:

```text
минимизировать ошибку между RUL_pred_h и RUL_oracle_h
```

В sklearn для `RandomForestRegressor` деревья строятся по критерию уменьшения MSE внутри листьев.

## 8. Балансировка обучения

В обучении используются веса строк:

```text
sample_weight = вес по run_id * вес по диапазону RUL
```

Зачем:

- чтобы длинные прогоны не задавили короткие только количеством строк;
- чтобы самые частые диапазоны RUL не задавили редкие;
- чтобы модель видела вклад разных прогонов и разных стадий ресурса более равномерно.

Это не меняет target, но меняет вклад строк в обучение.

## 9. Как проверяем, что модель учится тому, что надо

### 9.1. Нет target leakage

Входной список `ML_INPUT_COLUMNS` не содержит:

```text
RUL_oracle_h
clog_level
state
```

Отдельный тест проверяет, что изменение `RUL_analytic_h` не меняет ML-прогноз. Это важно, потому что аналитический RUL не должен быть скрытой подсказкой для модели.

### 9.2. Test состоит из других прогонов

Метрики считаются на `run_id`, которые не участвовали в train. Это проверяет обобщение на новые траектории, а не запоминание соседних точек.

### 9.3. Сравниваем с аналитикой

В отчете сохраняются:

```text
ML MAE / RMSE / R2
Analytic MAE / RMSE / R2
```

Если ML хуже аналитики на отдельных сценариях, это видно в метриках по `scenario`.

### 9.4. Смотрим текущий прогон против oracle

В UI есть “Ошибка на текущем прогоне”. Она использует скрытый `RUL_oracle_h` симулятора и показывает, насколько ML/аналитика/гибрид ошибаются на демонстрационном запуске.

Это не test-метрика модели, но хороший диагностический график для демонстрации.

## 10. Ограничение текущего подхода

RandomForest плохо экстраполирует за пределы распределения train-данных. Если модель никогда не видела RUL около `8000-9000` часов, она не сможет уверенно предсказывать такие значения.

Поэтому для здоровых режимов важны две вещи:

1. Добавлять в train-корпус длинные нормальные прогоны с известным `RUL_oracle_h`.
2. Передавать модели паспортные параметры объекта, особенно `k_s_per_hour`, `dp0_kpa`, `k_c`, `gamma_load`.

Иначе начальные участки разных сценариев выглядят слишком похожими по телеметрии, и модель будет возвращать усредненный RUL.
