# Процесс работы программы: от запуска до интерпретации вывода

Документ описывает, что делает прототип симулятора газового фильтра после запуска `main.py`, какие файлы он создаёт и как читать полученные результаты.

## 1. Запуск программы

Программа запускается из корня проекта:

```powershell
.\.venv\Scripts\python.exe main.py
```

Основной сценарий берётся из файла:

```text
configs/base.yaml
```

В нём задаются:

- длительность моделирования;
- шаг по времени;
- параметры расхода, давления и температуры;
- параметры деградации фильтра;
- пороги `warning` и `critical`;
- параметры шумов и дефектов датчиков;
- настройки LSTM-окон.

После запуска программа создаёт каталог:

```text
outputs/slow_clogging/
```

Название `slow_clogging` берётся из параметра `scenario_name` в конфигурации.

## 2. Общая схема работы

Полный конвейер выглядит так:

```text
configs/base.yaml
-> симуляция временного ряда
-> добавление шумов и дефектов датчиков
-> расчёт диагностических меток
-> экспорт CSV/Parquet
-> построение признаков
-> rule-based baseline
-> ML baseline
-> hybrid decision layer
-> LSTM-окна
-> графики
-> текстовые описания и метаданные
```

В текущей версии LSTM ещё не обучается. Программа готовит данные и окна для будущего обучения LSTM, обучает классические baseline-модели RandomForest и использует ML-RUL baseline как временный источник прогноза для гибридной логики.

## 3. Этап симуляции

На первом этапе программа генерирует синтетическую работу газового фильтра во времени.

Формируются основные физические каналы:

- `Q` - расход газа;
- `P_in` - давление на входе;
- `P_out` - давление на выходе;
- `deltaP` - перепад давления на фильтре;
- `T` - температура газа;
- `rho_rel` - относительная плотность газа;
- `clog_level` - скрытый уровень засорения.

Важно: `clog_level` является скрытой переменной симулятора. В реальной системе она напрямую неизвестна. Она нужна для проверки качества модели и построения обучающих целей.

## 4. Шумы и дефекты данных

После генерации clean-сигналов программа добавляет реалистичные проблемы наблюдений:

- шумы датчиков;
- пропуски;
- выбросы;
- залипание датчика;
- возможные физические нарушения.

Эти проблемы отражаются в колонках:

- `quality_code`;
- `fault_flags`.

Как читать:

- `quality_code = good` - строка пригодна для обычного анализа;
- `quality_code != good` - строка содержит проблему качества;
- `fault_flags` показывает конкретные причины, например пропуск, выброс или физическое нарушение.

Если данные плохого качества, будущая гибридная модель не должна слепо доверять ML-прогнозу.

## 5. Расчёт состояний и RUL

Программа рассчитывает несколько диагностических величин.

### Нормированный перепад давления

Ключевой диагностический признак:

```text
deltaP_norm_kPa
```

Он очищает перепад давления от влияния расхода и относительной плотности газа.

Смысл:

- сырой `deltaP_kPa` может расти из-за увеличения расхода;
- `deltaP_norm_kPa` лучше отражает именно рост сопротивления фильтра;
- состояние фильтра и RUL логичнее оценивать по нормированному перепаду.

### Состояние фильтра

Колонка:

```text
state
```

Возможные значения:

- `normal` - нормальный режим;
- `warning` - предупредительное состояние;
- `critical` - критический режим;
- `unknown` - состояние нельзя надёжно определить из-за качества данных.

Смысл порогов:

- ниже `dp_warn_kpa` - `normal`;
- между `dp_warn_kpa` и `dp_crit_kpa` - `warning`;
- выше `dp_crit_kpa` - `critical`.

### Oracle RUL

Колонка:

```text
RUL_oracle_h
```

Это истинный остаточный ресурс в часах до достижения критического состояния по clean-траектории симулятора.

Как читать:

- большое значение означает, что до критического состояния далеко;
- малое значение означает близость к критическому состоянию;
- `0` означает, что критический порог уже достигнут;
- пустое значение возможно, если в пределах горизонта симуляции критическое состояние не наступает.

Важно: `RUL_oracle_h` доступен только в синтетических данных. В реальной системе его нельзя подавать на вход модели.

### Аналитический RUL

Колонка:

```text
RUL_analytic_h
```

Это простая расчётная оценка остаточного ресурса. Она нужна как:

- baseline;
- fallback;
- sanity-check для будущего LSTM-прогноза.

Если будущий `RUL_LSTM` сильно расходится с `RUL_analytic_h`, гибридная система должна снижать доверие к прогнозу или отправлять случай на ручную проверку.

## 7. Файлы признаков

Файлы:

```text
features.csv
features.parquet
features_ru.csv
feature_description.md
```

Feature builder добавляет признаки:

- `deltaP_norm_kPa`;
- `deltaP_roll_mean_1h`;
- `deltaP_roll_std_1h`;
- `deltaP_slope_6h`;
- `Q_roll_mean_1h`;
- `missing_rate_1h`;
- `time_above_warn`.

Как читать:

- `deltaP_roll_mean_1h` показывает сглаженный перепад за 1 час;
- `deltaP_roll_std_1h` показывает нестабильность перепада;
- `deltaP_slope_6h` показывает скорость роста перепада;
- `missing_rate_1h` показывает долю проблемных данных за последний час;
- `time_above_warn` показывает, как долго фильтр находится выше warning-порога.

Эти признаки нужны для:

- анализа;
- rule-based логики;
- классических ML baseline;
- будущей интерпретации решений.

## 8. Rule-based baseline

Файлы:

```text
rule_baseline.csv
rule_baseline.parquet
rule_baseline_ru.csv
rule_baseline_description.md
```

Rule-based baseline - это простая регламентная логика.

Она определяет:

- `rule_state`;
- `rule_recommendation`;
- `rule_priority`;
- `rule_reason`.

Как читать рекомендации:

- `continue_monitoring` - продолжать мониторинг;
- `planned_maintenance` - запланировать обслуживание;
- `urgent_maintenance` - срочное обслуживание;
- `inspect_sensor_data` - сначала проверить данные или датчики.

Как читать приоритет:

- `P3` - низкий приоритет;
- `P2` - плановое действие;
- `P1` - срочное действие;
- `P0` - проблема данных, прогнозу доверять нельзя.

Важно: это простой baseline. Полная гибридная логика находится в отдельном файле `hybrid_decisions.csv` и использует confidence, fusion RUL, rule trace и объяснение решения.

## 9. ML baseline

Каталог:

```text
outputs/slow_clogging/ml_baseline/
```

Файлы:

```text
ml_predictions.csv
ml_predictions.parquet
ml_metrics.json
ml_baseline_report.md
random_forest_rul.joblib
random_forest_state.joblib
```

Что обучается:

- `RandomForestRegressor` для прогноза `RUL_oracle_h`;
- `RandomForestClassifier` для классификации `state`.

Как читать `ml_predictions.csv`:

- `state_true` - истинное/расчётное состояние;
- `state_pred` - предсказание классификатора;
- `RUL_oracle_h` - истинная цель;
- `RUL_pred_h` - предсказанный остаточный ресурс;
- `split` - принадлежность строки к train или test.

Как читать `ml_metrics.json`:

- `mae_h` - средняя абсолютная ошибка RUL в часах;
- `rmse_h` - среднеквадратичная ошибка RUL в часах;
- `r2` - качество регрессии относительно простой средней модели;
- `accuracy` - точность классификации состояния.

Если метрики слабые, это не обязательно ошибка симулятора. Baseline нужен как нижняя точка сравнения:

```text
правила
-> классический ML
-> LSTM
-> гибридная модель
```

Каталог:

```text
outputs/slow_clogging/hybrid/
```

```text
hybrid_decisions.csv

hybrid_decisions_ru.csv
hybrid_decision_logic.md
decision_packages.jsonl

```

Гибридный слой объединяет:

- состояние фильтра;
- качество данных;
- флаги сбоев;
- аналитический RUL;
- ML-прогноз RUL;
- доверие к данным;
- доверие к модели;
- согласованность ML и аналитики;
- продукционные правила.

Ключевые колонки:

- `RUL_ml_h` - прогноз RUL от текущей ML baseline-модели;
- `RUL_analytic_h` - аналитическая оценка RUL;
- `RUL_fused_h` - итоговый RUL после fusion;
- `rul_source` - источник итогового RUL;
- `confidence_data` - доверие к качеству данных;
- `confidence_model` - доверие к ML-прогнозу;
- `confidence_consistency` - согласованность ML и аналитического RUL;
- `confidence_total` - общее доверие;
- `action` - итоговое действие;
- `priority` - приоритет действия;
- `due_time_h` - срок выполнения в часах;
- `rule_trace` - список сработавших правил;
- `explanation` - человекочитаемое объяснение.

Файлы объяснений:

- `decision_packages.jsonl` - полный структурированный пакет объяснения для каждой временной точки;
- `decision_cards.md` - человекочитаемые карточки решений для последней точки и типовых действий.

Как читать `action`:

- `monitor` - продолжать мониторинг;
- `sensor_check` - проверить датчики;
- `planned_maintenance` - назначить плановое ТО;
- `urgent_maintenance` - назначить срочное ТО;
- `shutdown_request` - запросить останов;
- `manual_review` - передать случай на ручную проверку.

Как читать `rul_source`:

- `ml_baseline` - использован ML-прогноз;
- `conservative_min` - взят минимум между ML-RUL и аналитическим RUL;
- `analytic_fallback` - использована аналитическая модель;
- `analytic_data_veto` - ML-прогноз заблокирован из-за качества данных.

Важно: сейчас `RUL_ml_h` является временным заменителем будущего `RUL_LSTM_h`. После обучения LSTM архитектура decision layer останется той же, поменяется только источник прогноза.

## 11. LSTM-окна

Каталог:

```text
outputs/slow_clogging/lstm_windows/
```

Файлы:

```text
lstm_rul_windows.npz
lstm_state_windows.npz
lstm_windows_metadata.json
lstm_windows_description.md
```

Основная задача для LSTM в первой версии:

```text
прогнозировать RUL_oracle_h
```

Формат:

```text
X.shape = (samples, sequence_length, features)
y.shape = (samples,)
```

В текущей конфигурации:

- окно: 24 часа;
- шаг данных: 5 минут;
- `sequence_length = 288`;
- число входных признаков: 7.

Входные признаки:

- `P_in_MPa`;
- `P_out_MPa`;
- `deltaP_kPa`;
- `Q_m3h`;
- `T_C`;
- `rho_rel`;
- `deltaP_norm_kPa`.

Как читать:

- один sample - это окно истории за последние 24 часа;
- `X[i]` содержит последовательность телеметрии;
- `y[i]` содержит целевой RUL в текущий момент;
- эти файлы являются подготовкой к обучению LSTM, а не результатом обученной нейросети.

## 12. Графики

Каталог:

```text
outputs/slow_clogging/plots/
```

Основные графики:

- `00_obzornyi_dashboard.png` - обзор всех ключевых рядов;
- `01_rashod_q.png` - расход газа `Q(t)`;
- `02_davleniya_pin_pout.png` - входное и выходное давления;
- `03_perepad_delta_p.png` - сырой перепад давления;
- `04_zasorenie_clog_level.png` - скрытое засорение;
- `05_ostatochnyi_resurs_rul.png` - oracle и аналитический RUL;
- `06_sostoyanie_filtra.png` - raw-состояние и сглаженное устойчивое состояние фильтра;
- `07_normirovannyi_perepad.png` - нормированный перепад;
- `08_delta_p_i_zasorenie.png` - сравнение перепада и засорения.

Как читать графики:

1. Сначала открыть `00_obzornyi_dashboard.png`.
2. Проверить, что `clog_level` плавно растёт.
3. Сравнить `deltaP_kPa` и `deltaP_norm_kPa`.
4. Если сырой `deltaP_kPa` шумный, это нормально: он зависит от расхода.
5. Проверить, что `deltaP_norm_kPa` показывает более устойчивый тренд засорения.
6. Проверить, что `RUL_oracle_h` уменьшается при приближении к critical.
7. Проверить, что устойчивое состояние переходит от `normal` к `warning` и `critical`.
8. Краткие всплески `unknown` читать как проблемы качества данных, а не как мгновенное физическое восстановление или деградацию фильтра.

Ключевая проверка:

```text
если clog_level растёт, а deltaP_norm_kPa тоже показывает восходящий тренд,
то симулятор ведёт себя физически согласованно.
```

Важно: сглаживание применяется только на графике состояния. Колонка `state` в датасете не сглаживается, чтобы не потерять информацию о качестве данных и кратких аномалиях.

## 14. Как читать консольный вывод

После запуска программа печатает:

```text
Сгенерировано строк: ...
Сценарий: ...
Строк с флагами качества: ...
Созданные файлы:
...
Созданные признаки:
...
Создан rule-based baseline:
...
Обучен ML baseline:
...
Создана гибридная логика решений:
...
Созданы LSTM окна:
...
Созданные графики:
...
```

Смысл:

- `Сгенерировано строк` - размер временного ряда;

- далее перечисляются все созданные файлы.

Если файл указан в консоли, значит соответствующий этап pipeline завершился успешно.

## 15. Что считать итоговым результатом текущей версии

outputs/slow_clogging/hybrid/hybrid_decisions.csv

Остальные артефакты нужны для анализа, обучения и проверки:

- `features.csv` - признаки;

- `lstm_windows/*.npz` - подготовка к обучению LSTM;

## 16. Что будет итогом будущей LSTM-гибридной версии

Следующий этап должен заменить временный ML-RUL baseline на LSTM-прогноз.

Итоговый вывод уже имеет нужную структуру:

- `action`;
- `priority`;
- `due_time_h`;
- `RUL_ml_h`, позднее `RUL_LSTM_h`;
- `RUL_analytic_h`;
- `RUL_fused_h`;
- `confidence_total`;
- `quality_code`;
- `fault_flags`;
- `rule_trace`;
- `explanation`.

Пример будущей интерпретации:

```text
Действие: planned_maintenance
Приоритет: P2
Срок: в течение 72 часов
Причина: фильтр находится в warning-состоянии, RUL ниже планового горизонта,
качество данных хорошее, аналитическая оценка согласована с ML-прогнозом.
```

В текущей версии эту роль выполняет `hybrid_decisions.csv`. Ограничение только в том, что ML-прогноз пока получен RandomForest baseline, а не LSTM.
