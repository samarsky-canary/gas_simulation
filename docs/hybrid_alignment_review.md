# Проверка соответствия текущей ML-версии

Дата проверки: 2026-05-14.

## Короткий вывод

Текущий прототип зафиксирован как ML-only версия: симулятор формирует телеметрию и целевые метки, feature builder строит диагностические признаки, RandomForest baseline прогнозирует RUL, а гибридный rule-based слой превращает прогноз в объяснимую рекомендацию по обслуживанию.

## Что входит в текущий контур

```text
симулятор
-> фиксированный датасет
-> feature builder
-> rule-based baseline
-> RandomForest ML baseline
-> confidence
-> RUL_fused_h
-> rule engine
-> action + priority + due_time_h + explanation
-> графики и карточки решений
```

## Что проверено методически

1. Датасет имеет фиксированный контракт колонок:
   `run_id`, `timestamp`, `filter_id`, `scenario`, `P_in_MPa`, `P_out_MPa`, `deltaP_kPa`, `Q_m3h`, `T_C`, `clog_level`, `deltaP_norm_kPa`, `state`, `RUL_oracle_h`, `RUL_analytic_h`, `quality_code`.
2. Входы ML-моделей ограничены наблюдаемыми и производными признаками:
   `P_in_MPa`, `P_out_MPa`, `deltaP_kPa`, `Q_m3h`, `T_C`, `deltaP_norm_kPa` и признаки feature builder.
3. Скрытые и целевые переменные не используются как входы:
   `clog_level`, `RUL_oracle_h`, `state`.
4. `deltaP_norm_kPa` нормируется по расходу:
   `deltaP_kPa / max((Q / Q_nominal)^alpha_flow, eps)`.
5. `state`, `RUL_oracle_h`, `RUL_analytic_h` и rule-based baseline опираются на нормированный перепад, а не на сырой `deltaP_kPa`.
6. Гибридный слой учитывает качество данных, согласованность ML и аналитического RUL, итоговое доверие и правила безопасности.
7. ML baseline обучается на корпусе из нескольких независимых `run_id`, а test состоит из других seed основных сценариев и стресс-сценариев качества данных.

## Реализованные блоки

- Симулятор эксплуатации фильтра.
- Экспорт CSV/Parquet и русифицированных CSV.
- Feature builder.
- Rule-based baseline.
- RandomForestRegressor для `RUL_oracle_h`.
- Гибридный decision layer.
- Пакеты объяснения решений и Markdown-карточки.
- Диагностические графики.

## Текущий смысл гибридной модели

ML-модель отвечает за прогноз RUL. Аналитическая модель используется как физически интерпретируемый baseline и fallback. Rule-based слой проверяет качество данных, согласованность прогнозов, выбирает итоговый RUL и формирует действие:

- `monitor`;
- `sensor_check`;
- `planned_maintenance`;
- `urgent_maintenance`;
- `shutdown_request`;
- `manual_review`.

## Что сознательно не входит в текущий этап

Нейросетевые модели и оконная подготовка временных рядов сейчас исключены из кода и документации. Текущая версия должна быть самодостаточной ML-only системой, которую можно проверять, описывать и сравнивать с rule-based baseline.

## Итоговая формулировка для работы

Классическая ML-модель прогнозирует остаточный ресурс газового фильтра по телеметрии и диагностическим признакам, аналитическая модель используется как интерпретируемый baseline и fallback, а продукционная система правил выполняет проверку качества данных, оценку согласованности прогнозов, выбор итогового RUL и формирование объяснимой рекомендации по техническому обслуживанию.
